# Multi-project EF Core API architecture

Derived from PequenosTalentosApi: sibling PequenosTalentos.Api, .Service, .Repository, and .Model projects targeting .NET 6, with ASP.NET Core controllers split into APP/Admin routes, constructor-injected service and repository interfaces, EF Core 6 with SQL Server and parameterized SQL, shared response envelopes, JWT startup configuration, and a typed external correction-service client. Versions describe the supplied reference, not a runtime upgrade recommendation.

Eleven independent C# patterns cover bootstrap, controller, application service, repository, DbContext, model, DTO, enum, request, response, and external HTTP client. Service, repository, request, and HTTP client patterns bundle related files; interface destinations retain Interfaces subdirectories. Unlike the existing dotnet-multiproject family, this variant uses EF Core, sibling projects, and service-owned response envelopes rather than PetaPoco/SQLKata, Application/Infrastructure/Contracts directories, or scheduled jobs.

The examples generalize the educational domain to items, retain Sucesso/Mensagem/StatusCode/Dados envelopes and the Dados request wrapper, and preserve parameterized SQL and write transactions. Adaptations add cancellation, safe public error messages, explicit nullable defaults, input contracts, and controller HTTP status mapping. The source often returns envelopes directly with HTTP 200 regardless of the envelope status; the examples map statuses deliberately. ModelState validation and authentication failures retain framework handling, so the sample does not promise a global envelope for every response. Client-provided identity fields from the original Request<T> are omitted because they cannot establish caller authority.

The Repository ApplicationDbContext is the context registered by the reference composition root. A separate Data/ApplicationDbContext exists in the archive but is not referenced by the inspected API, Service, or Repository project files; it is not promoted into a second persistence layer. NPoco is declared as a dependency in the archive, but these examples represent the EF Core path observed in the inspected repositories.

JWT issuer, audience, lifetime, and signing-key validation remain at startup. The reference also has a custom_token validation hook and an additional middleware file that is not wired in Program.cs. The examples do not reproduce its custom cryptography, log tokens, activate that middleware, implement token issuance, or claim equivalent application-specific authentication. Add the required verification and authorization policy explicitly in a consuming application. Admin routing alone is not an administrative permission policy.

Only C# structural examples are installed. No appsettings, connection strings, keys, launch settings, publish profiles, project-user files, solution files, project manifests, database schema, or deployment configuration are copied. External endpoints and credentials remain supplied by the consuming application. SQL examples assume a matching schema; keyless DTO mapping demonstrates query projections without creating tables or migrations.

Resolve the nearest project scope before choosing a pattern. These examples are structural references rather than a runnable API installer. Catalog and C# syntax checks do not prove dependency compatibility, database integration, JWT policy, or external service behavior in the original .NET 6 application.
