# Flutter Provider layered architecture

Derived exclusively from the 125 `.dart` entries in the supplied PWA.zip. The inspected source groups Flutter feature pages, HTTP services, schemas (models, DTOs, requests, numeric enums), reusable shared widgets, theme preferences, Provider session state, and builder-based navigation guards. This is the project's conventional layered organization; it does not imply Clean Architecture, BLoC, or Riverpod.

The thirteen independent patterns contain only Dart examples, stored as typed `.dart.md` documents with `.dart` destinations. Archbase manifests, rule definitions, and catalog documentation retain their own native formats. No archive assets, pubspec files, lockfiles, web/native platform files, generated Firebase configuration, project endpoints, or other non-Dart source files are copied. Dependency versions are not inferred because only Dart source was inspected.

Preserve the lib/pages, lib/services, lib/schemas, lib/shared, and lib/style boundaries. Keep DTO and request directories distinct from the core models. The source's notificacao_provider.dart actually owns AuthProvider session state; that filename is retained in the reference. Cards, form fields, filters, items, and modals share the widget pattern and constructor/callback convention. Resolve the nearest scope before selecting a structural pattern; overlapping general and specialized rule globs describe compatibility rather than activating multiple patterns.

Examples generalize the educational domain to items. Unlike the reference's directly constructed services and repeated preference reads, the sample composition root shares injectable services and session state through Provider. Routes are collected in routes.dart, invalid identifiers are rejected, asynchronous state updates check mounted, and redirects are scheduled once after a frame. The API sample retains serialized bearer-authenticated GET/POST requests but settles each future after failure instead of clearing unresolved completers. Services retain the sucesso/dados envelope and propagate errors instead of presenting them as empty lists. A 401 invalidates the local session; other HTTP failures are reported to the page. Theme handling retains ValueNotifier and brightness observation without brand colors or assets.

SharedPreferences mirrors the inspected session convention; token presence is only a local navigation hint, not server-side verification, and consumers must choose storage and session validation appropriate to their target platform. Role and guest guards follow the same widget boundary but require explicit policy in a consuming app. Authentication screens, Firebase startup, localization, URL strategy, and feature-specific integrations are not reconstructed. The authentication route and detail view are intentionally minimal structural views.

Examples are references, not a complete application generator. Catalog, Dart parsing/formatting, and MCP tests do not prove a Flutter build, web installation behavior, Firebase integration, or backend authentication. No dependencies are added to Archbase or installed into a consuming project.
